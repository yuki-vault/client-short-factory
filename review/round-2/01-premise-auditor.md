## findings

### [F-01-001] P0の成立確認だけでは、6〜9日のHermes UIが最短経路だと決まらない

- **対象**: §4.2 / 「4項目のどれかが成立しなければUI実装を始めず、既存CLI＋file reviewへ縮退する。」
- **主張**: 4項目はUI実装の可否しか測らず、既存CLI＋file reviewがS-01 / S-02 / S-04と最初のmilestoneをより短く満たせるかを比較しない。P0が成功しただけでP1へ進むと、「最短で到達する」という目的に対して6〜9日の経路を無根拠に選ぶ。
- **再現条件**: 開発者がP0の4項目を順に確認して全項目を成立と判定する → §4.2に従ってCLI＋file reviewへ縮退せずP1を承認する → P1のUI・full playback・approval処理を実装する → 後から既存CLI＋file reviewでも1語修正、revision固定render、QC/content分離、current identity照合を完走できたと判明し、先行実装を捨てる。
- **反証条件**: P0で既存CLI＋file reviewを同じmilestoneと3安全条件に対して実走し、いずれかを満たせない記録が残る場合。
- **影響区分**: 半日
- **severity**: must_fix
- **最小修正案**: P0を「UI可否」ではなく「最短経路選択」に縮退し、scratchでCLI＋file reviewによる1語修正→revision固定render→QC/content別記録→current identity照合を先に実走する。これが通ればそれを初期milestoneとして停止し、通らない項目がある場合だけP1の該当部分を開始する。
- **検証方法**: `P0-shortest-route-gate` — P0報告に4つのmilestone操作の成立/不成立と選択経路があり、全項目成立時にはproduct UI変更が0件で停止することを確認する。
- **追加コスト**: 0.0 人日
- **交換に削除する項目**: なし

### [F-01-002] P0では測れないP1見積が、15日停止条件の入力になっている

- **対象**: §11 / 「P1の6〜9日はRound 1の実質見積であり、P0結果で再見積する。」
- **主張**: P0が測るのは再生・seek・入口・再接続であり、P1の7実装項目それぞれの再利用量や残作業量ではない。それでも6〜9日をP0〜P2合計と§10の15日停止判定に使うため、数字を更新しても測定根拠が増えない。
- **再現条件**: 開発者がP0を0.25日で通過する → 根拠が4接続項目だけのままP1を6〜9日として承認する → 8日消化時点で未着手項目の上側見積を8日と置く → `actual burn + 未着手上側見積 > 15日`となり§10で停止し、未完の縦切りだけが残る。
- **反証条件**: P0終了報告にP1の7項目ごとの既存再利用箇所、実走結果、欠落項目、残作業上側見積が記録され、その合計から6〜9日が再計算される場合。
- **影響区分**: 半日
- **severity**: must_fix
- **最小修正案**: P0前の「6〜9日」と「7.75〜11.75日」を確定値として使わず、P0でP1の7項目を `実走済み / 再利用のみ / 新規` に分けた後にだけ上側見積を置く。15日超ならP1開始後ではなく開始前にCLI＋file reviewへ縮退する。
- **検証方法**: `P0-estimate-evidence-check` — P1承認前に7項目すべての分類と根拠があり、その合計が§5と§10の数字に一致することを確認する。
- **追加コスト**: 0.0 人日

### [F-01-003] previewだけを見るP3では、未測定のcandidate見逃し率を検出できない

- **対象**: §6.4 / 「人間は長時間sourceではなくpreviewだけを確認し」
- **主張**: §11はcandidate見逃し率を未測定と認める一方、§7の成功条件は提示された候補同士だけを評価する。これでは「AIが最良区間を候補に含めたか」と「候補内のpaced版がbaselineより良いか」が混ざり、候補探索を検証しないままP3が成功扱いになる。
- **再現条件**: holdout source内の最良区間XをAIが5候補から外す → 人間がsourceを見ず提示previewだけを確認する → その中のpaced版をbaselineより良いと選び、semantic cut error 0で§7を通過する → 後日source全編を見てXを発見し、1〜2日かけたP3が候補探索の根拠にならないと判明する。
- **反証条件**: P3の結論をpaced recipeだけに限定し、candidate discoveryは人間が事前固定したholdoutの第一候補をAI候補集合が含むまで未検証扱いにする場合。
- **影響区分**: 半日
- **severity**: must_fix
- **最小修正案**: P3を「人間が指定した同一candidate上のbaseline対paced比較」に縮退し、candidate見逃し率を結論から外す。candidate UI化のgateは、別途holdoutで人間の事前固定top-1をAI候補が含む計測ができるまで閉じる。
- **検証方法**: `P3-claim-separation-check` — P3 resultにpaced品質の結論とcandidate discoveryの結論が別欄であり、top-1包含の観測なしでは後者が「未検証」になることを確認する。

### [F-01-004] delivery ledgerの4項目だけでは「前に送ったやつ」の対象を一意に選べない

- **対象**: §4.7 / 「client | delivered_at | output_hash | caption_revision」
- **主張**: ledgerにjob/source/納品時の表示名がなく、clientの自然言語による修正依頼とhashを結ぶ根拠がない。複数jobを同じclientへ送った時、誤ったcaption revisionを新working revisionへcopyして誤納品できる。

- **反証条件**: `output_hash`からclientが用いる納品名とjobへ一意に引ける索引が既にあり、その所在と照合手順が§4.7に明記される場合。

- **検証方法**: `delivery-recall-two-jobs` — 同一clientのA/Bをtest ledgerへ記録し、「商品A」の依頼からAのjob_id・hash・caption revisionだけが選ばれることを手順確認する。

### [F-01-005] content reviewを連続全編再生に限定する規則は削除すべき

- **対象**: §4.5 / 「seekと速度変更を無効化する。」
- **主張**: S-02が要求するのはtechnical QCと内容確認を同一表示にしないことであり、0秒から1倍速で連続再生することではない。この無根拠な同一視が、tab/source/seek監視の実装と最大180秒の強制作業を全revisionへ課す。
- **再現条件**: 開発者がP1のfull-playback state、seek/速度無効化、tab非表示無効化を実装する → userがR1を全編確認する → 固有名詞1語を直してR2をrenderする → 内容の変更箇所以外も0秒から終端まで再度1倍速再生しない限りapprovalへ進めない。
- **反証条件**: 連続全編再生をしない内容確認が原因となった誤納品の観測、またはclientが連続1倍速確認を要求する契約が存在する場合。
- **影響区分**: 半日
- **severity**: reject
- **最小修正案**: §4.5のcoverage獲得、seek/速度禁止、tab/sourceによる試行無効化を削除する。`output_hash + caption_revision`に結び付いた明示的な「内容確認済み」操作だけを残し、technical QCから自動継承しないことでS-02を守る。
- **検証方法**: `content-state-separation-without-playback-policing` — technical QC成功だけではcontent未確認、明示確認後だけ確認済み、caption/render変更後は再び未確認になることを確認する。
- **追加コスト**: -1.0 人日
- **交換に削除する項目**: なし

### [F-01-006] 単発10分をP3提案条件にする§8.1は削除すべき

- **対象**: §8.1 / 「実案件でsource探索またはpacing手修正が1job 10分以上を占めた。」
- **主張**: 1回10分という観測には、1〜2日のoffline spikeを回収できる案件本数・再発率・品質価値の根拠がない。client 1〜2社・納品実績0本の段階では、単発の10分超だけを投資再開の根拠にできない。
- **再現条件**: 最初の実案件でpacing手修正を10分行う → §8.1成立を理由にP3を提案・承認する → 1〜2日かけてoffline spikeを完了する → 同種のjobが再発せず、削減対象は最初の10分だけで終わる。
- **反証条件**: 同種のjobが少なくともP3の1〜2日を回収する本数だけ受注済み、またはclientの明示要件・案件化不能という§8.2/§8.3の品質根拠がある場合。
- **影響区分**: 半日
- **severity**: reject
- **最小修正案**: §8.1を削除し、現時点の再開条件はclient明示要件または案件化不能という§8.2/§8.3だけにする。時間削減による再開は、同種jobの確定本数と累計手作業時間がP3 timeboxを上回った時だけ再提案する。
- **検証方法**: `P3-reopen-reason-check` — P3提案書が§8.2/§8.3のどちらか、またはP3 timeboxを上回る確定累計手作業時間を示し、単発10分だけでは開始不可になることを確認する。

## 検査済み・問題なし

- **§1.1 字幕ボトルネックの一般化**: 5分・約90%という1本の結果を「主要ボトルネック」と一般化していない。creative課題と未決事項を分離しており、この攻撃では破れなかった。
- **§4.2 Hermes player/backend前提**: 実機未検証のままP1へ依存していないかを攻撃した。P0で再生・seek・save/render入口・再接続を実測し、失敗時はproduct code変更前に停止するため、成立可否そのものは安全に封じている。
- **§5 180秒上限**: 技術的不安から尺を決めていないかを攻撃した。90秒ではなくimplementation promptと配信先の公式Helpに結び、配信先変更時だけ見直すため、本文上は案件側の根拠へ戻されている。
- **§6.3 paced recipe**: AIが意味変更を自動確定する前提を攻撃した。source順・non-overlap・削除対象を限定し、意味を変えるjoinは人間確認へ残し、初期productから外しているため破れなかった。
- **§4.1 rights記録**: immutable attestationや権限基盤を復活させていないかを攻撃した。1枚のtext fileに縮退し、payload差分は今回の許可差の観測に限定されているため過剰前提ではない。
- **§5 P2 修正版pilot**: 「clientは修正依頼を出さない」という暗黙前提を攻撃した。R1からR2を作り、旧版を保持して再承認する操作列がある。過去納品の識別子不足だけはF-01-004として分離した。
- **§9 初期scope外**: client増加を先読みしてDB・queue・複数worker・portalを要求していないかを攻撃した。すべて明示的にscope外であり、共有前提に反する復活はない。

## 他エージェントと対立しうる立場

- F-01-001は、Hermes UIの構築自体が元promptの固定要件なら「最短経路比較は不要」と反論されうる。ただし本文§2.1は状態到達をmilestoneに置き、§4.2自身がCLI＋file reviewを有効な縮退先としているため、本レビューは経路が未固定だと解釈した。
- F-01-002は、6〜9日を拘束力のない仮置きとみなす立場と対立する。本文ではその数字が合計見積と15日停止条件へ実際に使われるため、単なる参考値とは扱わなかった。
- F-01-003は、P3がpaced recipeだけを評価しcandidate discoveryを評価しないという解釈と対立する。§2.2、§6.2、§6.4、§7が0〜5候補とpreview-only reviewを同じlaneに置くため、現状は両者を分離できていないと判定した。
- F-01-004は、`output_hash`からjobを検索できる既存索引が別途あるなら不要になる。その索引は対象draft内に根拠がないため、反証条件に置いた。
- F-01-005は、内容確認とは必ず全編1倍速再生であるという安全重視の立場と対立する。本レビューではS-02の文言を超える確認方式は事故観測かclient要件がない限り自己負担の追加規則と判定した。
- F-01-006は、P3を時間回収ではなく学習投資として許す立場と対立する。学習・品質目的は§8.2/§8.3で既に扱えるため、時間だけを根拠にする§8.1は削除対象とした。
