# Agent 01 — Premise Auditor — Round 1

## 総括（3行以内）

中心目的が「字幕を手編集せず直し、最新版を承認する」から長尺候補探索・multi-cutへ先に移っており、その優先順位は未計測である。
2素材の結果で閾値を後決めし、その同じ結果でproduct化を判断するgateは反証にならない。
また、納品済み版からの修正とreview UIの動画経路が無根拠のままで、謝罪または半日以上の手戻りになる操作列が残る。

## findings

### [F-01-001] 未計測の長尺探索を先行させ、唯一の完了目的をW5まで遅らせている

- **対象**: §2.1 / 「ユーザーが長時間sourceを通して見ずに、AIが提示した最大5本の短いpreviewだけを見て」
- **主張**: この目的変更を支えるのは1素材の自己申告と仮説だけである。それでも§9ではW0/W1/W3、条件次第でW4までを、字幕修正・current render承認を提供するW5より前に置き、1人開発で途中停止したとき成果ゼロになる。
- **再現条件**: 開発者が記載順にW0を実施し、2素材のW1を行い、W2後にW3を実装し、paced版が1本でも選ばれたためW4へ進み、見積超過または疲弊でW5着手前に停止する。その時点で1.75〜5.25人日を字幕の手編集廃止にも最新版承認にも使えないartifactへ費やしている。
- **反証条件**: 字幕修正・承認より候補探索またはpacingが先でなければ初回納品を完了できないことが、別々に測ったactive timeまたは明示的なユーザー優先順位で示される場合。
- **影響区分**: 半日
- **severity**: must_fix
- **最小修正案**: §2の当面の完了像を「plain caption edit、明示render、current一致、内容承認」に戻し、W2直後にその最小W5とW7を置く。W1/W3/W4は最初の完走後へ移し、長尺探索は第二目的と明記する。
- **検証方法**: `plan-first-value-walkthrough` — Phaseを上から実行した想定で、最初の停止可能地点までにASSを直接触らず字幕を保存し、current renderだけを内容承認できることを確認する。
- **追加コスト**: 0 人日
- **交換に削除する項目**: なし

### [F-01-002] 初回2素材で閾値を後決めするgateはmulti-cut採用を反証できない

- **対象**: §7.1 / 「時間短縮の合格値は初回2素材を測ってから決める。」
- **主張**: 最初の2素材が閾値の作成用であると同時にW4採否の判定用でもあり、paced版が1本選ばれただけで1〜2人日のproduct統合へ進める。§13.1で標本数を未解決と認めたまま、肯定分岐だけが実行計画に固定されている。
- **再現条件**: 開発者がslow-talkと高密度sourceでA/Bを作り、slow-talkだけpaced版を主観選択し、同じ2件の測定値を見て合格値を設定し、W4を実装する。その後の実案件が連続切り抜きだけなら、W4の1〜2人日が使われない。
- **反証条件**: W1前に数値閾値と対象source母集団を固定し、閾値作成に使っていないholdoutまたは実案件がその閾値を満たす場合。
- **影響区分**: 半日
- **severity**: must_fix
- **最小修正案**: 2素材W1は棄却専用に縮退する。2本ともpaced不採用ならW4を落とせるが、1本以上の採用だけではW4へ進めず、W1後に固定した閾値を次の実案件1本が満たした時だけ再検討する。
- **検証方法**: `W4-gate-decision-table` — 「paced 0/2」「paced 1/2」「paced 2/2」とholdout有無を入力し、holdoutなしでは全ケースがW4保留になることを確認する。
- **追加コスト**: 0 人日
- **交換に削除する項目**: なし

### [F-01-003] 納品した版を特定しないcurrent-only契約では「前に送ったやつ」を誤って直す

- **対象**: §7.2 / 「current caption revisionとrenderの一致」
- **主張**: currentの整合性は保てても、どのoutputを誰へいつ送ったかが無いため、過去納品物を修正起点として特定できない。これはクライアントが過去版の修正を頼まないという無根拠の前提であり、別版を基に再納品する操作列が成立する。
- **再現条件**: 担当者がR1をclientへ手動送付し、その後別修正でR2をcurrentにし、clientから「前に送ったR1の固有名詞だけ直して」と依頼を受け、UIが示すcurrent R2へその修正を加え、R1には無かった変更を含むR3を送付する。clientが差分を発見し、誤った版を再送した説明と再納品が必要になる。
- **反証条件**: client、納品日時、output hash、caption revisionを結ぶ既存記録があり、過去納品版を修正起点として一意に選べる場合。
- **影響区分**: 謝罪
- **severity**: must_fix
- **最小修正案**: 自動deliveryは作らず、既存のimmutable renderとcaption revisionに対して、手動送付時に `client / delivered_at / output_hash / caption_revision` の1行を追記するテキスト台帳だけを完了像とW7へ入れる。修正依頼はその行のrevisionを複製して新revisionにする。
- **検証方法**: `prior-delivery-revision` — R1送付を記録し、R2をcurrentにした後にR1修正を指示し、選択元がR1のcaption revisionかつ新output hashになることを確認する。
- **追加コスト**: 0 人日
- **交換に削除する項目**: なし

### [F-01-004] W5はHermes backendと動画再生経路を未観測のまま2〜3日見積もっている

- **対象**: §9 W5 / 「current video再生」
- **主張**: 設計書にはHermes pluginが必要なbackend APIを持てる根拠コードも、認証付き取得からBlob URL等で動画を再生・seekできた観測もない。§4.6の全編再生とjoin前後previewまで同じ推測に依存し、W5開始時に崩れると2〜3日枠と先行統合作業が手戻りになる。
- **再現条件**: 開発者がW0〜W4を終えてW5を開始し、current renderとsource-map区間をbrowserへ渡すrouteを既存Hermes pluginに追加しようとし、想定したbackend hookが無いか、認証応答をvideo要素でseek再生できず、媒体配信経路とUI構成を作り直す。
- **反証条件**: Hermes実装のbackend API該当箇所を設計書が引用し、現行の認証条件で対象MP4の全編再生と任意seekを実機観測した記録がある場合。
- **影響区分**: 半日
- **severity**: must_fix
- **最小修正案**: W5見積の前提欄に実コード引用を置き、W0内で既存MP4 1本の再生・seekだけを無変更probeする。失敗時はW5を停止し、UIを前提にしない既存CLI＋ファイル運用へ縮退する。
- **検証方法**: `review-media-path-probe` — Windowsローカル実機でcurrent MP4を開き、先頭・中間・末尾へseekし、再読込後も同じcurrent hashの動画を再生できることを記録する。
- **追加コスト**: 0 人日
- **交換に削除する項目**: なし

### [F-01-005] client要件のないstyle preset工程は現在の設計から削除すべきである

- **対象**: §9 W6 / 「1つのfont / color / punch-in presetをfileで固定する。」
- **主張**: clientのbrief、brand guide、既存納品評価のいずれもないのに、0.5〜1日を使ってpresetを先回りで固定している。§13.5で品質差に十分か未解決と認めており、明示目的にも安全条件にも寄与しないため、現フェーズの設計項目として置く根拠がない。
- **再現条件**: 開発者がW5後に仮のfont・color・punch-inを0.5〜1日で調整し、W7のinternal pilotを通し、初clientからbrand font・色・punch-in禁止の指定を受け、W6成果を全て捨てて設定し直す。
- **反証条件**: 最初のclientから再利用可能なbrand guideとpreset受入条件が既に提示されている場合。
- **影響区分**: 半日
- **severity**: reject
- **最小修正案**: §4.7、§9 W6、§13.5を削除し、初回は現行caption styleをそのまま使う。実clientから具体的なstyle変更が出た時点で別途判断する。
- **検証方法**: `scope-trace` — 残る全Phaseの各成果物を「字幕修正」「current承認」「S-01/S-02/S-04」のいずれかへ結び、style専用成果物が0件であることを確認する。
- **追加コスト**: -0.5 人日
- **交換に削除する項目**: §4.7 Stage F、§9 W6、§13.5

### [F-01-006] 根拠のない180秒を安全kernelの制約に混ぜている

- **対象**: §9 W2 / 「global OS lock、3境界fault test、180秒制約。」
- **主張**: `180秒`にはclient契約、対象配信先、現行公式仕様の引用がなく、S-01/S-02/S-04にも属さない。正しい値であっても根拠分類は推測であり、最小安全kernelへ固定する理由がない。
- **再現条件**: 開発者がW2で180秒を一律上限として実装し、後から対象clientが別配信先の181秒素材を指定し、入口で拒否されたjobのために制約を外して再実行する。
- **反証条件**: 対象を特定プラットフォームへ固定するclient要件と、180秒を支える現行公式仕様URLが設計書に記載される場合。
- **影響区分**: 10分
- **severity**: should_fix
- **最小修正案**: W2から180秒制約を削除する。配信先が決まった時だけ、その配信先要件として別gateへ置く。
- **検証方法**: `W2-safety-scope-review` — W2の各項目がS-01/S-02/S-04のいずれかへ対応し、未引用のduration値が無いことを確認する。
- **追加コスト**: 0 人日

## 検査済み・問題なし

- §1.1〜§1.3に対し、観測・自己申告・仮説の混同を攻撃した。三者が明示的に分離され、「2時間」を正式baselineへ使わないため、この点自体は破れなかった。
- §3.2に対し、未確定なcut recipeがstale renderを承認可能にする操作列を試した。Creative Spikeをscratchに閉じ、approval・download・deliveryへ接続しないため、現段階ではS-01/S-04を破れなかった。
- §4.2に対し、heatmap取得不能が全処理を停止させるかを試した。複数clientでの取得失敗を観測根拠にoptional warningへ縮退しており、必須前提にはなっていない。
- §7.2に対し、technical QCだけで内容確認済みになるかを試した。`human content review complete`を独立gateにしているためS-02を破れなかった。
- §10に対し、見積超過時に安全条件まで削られるかを試した。削除順を明記し、S-01/S-02/S-04を削除対象外としているため、この攻撃では破れなかった。
